ProxyKubeApi spec.

## Example

```yaml
apiVersion: weebo.si.rs/v1
kind: ProxyKubeApi
metadata:
  name: my-proxykubeapi
  namespace: team-a
spec:
  cert:
    SystemRoots: true
  service:
    KubernetesService:
      name: kubernetes
      namespace: default
      port: 443
```

| [`jwt`](#spec.auth_config.jwt) | `object[]` | no | `[]` | Bounded so the quadratic uniqueness rule above stays inside the apiserver's CEL cost budget — the estimator multiplies this bound by the bound on `issuer.url`, and an unbounded pair is rejected outright. **Rules**

- validate_against is set to OidcProvider but the OIDC provider is not enabled — `self.validate_against != 'OidcProvider' || self.oidc_provider.enabled`
- validate_against is set to JwtAuthenticators but no jwt authenticator is configured — `self.validate_against != 'JwtAuthenticators' || size(self.jwt) > 0`
- two jwt authenticators are configured for the same issuer; only the first would ever apply — `self.jwt.all(a, self.jwt.exists_one(b, b.issuer.url == a.issuer.url))`

### `spec.auth_config.oidc_provider` [#spec.auth_config.oidc_provider]

| `client_id` | `string` | no | `""` | Ignored when the `config_from` Secret carries a `client_id` key. See `issuer_url` for why it is optional. |
| `client_secret` | `string` | no |  | The OAuth client secret, inline.<br /><br />Prefer `config_from`: a value here is readable by anyone with `get` on this resource, shows up in `kubectl get -o yaml`, and is copied into every backup of it. |
| [`config_from`](#spec.auth_config.oidc_provider.config_from) | `object` | no |  | Read the provider block from an external Secret instead of inlining it here.<br /><br />The Secret's keys are the snake_case field names of this struct — `issuer_url`, `client_id`, `client_secret`, `audience`, `extra_scope` — and any key it carries wins over the inline value; keys it does not carry fall back to the inline value, so a partial Secret (the common case: just `client_secret`) works. Keys outside that set are ignored, since a Secret managed by external-secrets is routinely shared with other consumers.<br /><br />The policy toggles (`enabled`, `accept_authorized_party`, `expose_oauth_authorization_server`) are deliberately *not* readable from the Secret: they decide how strictly tokens are validated and who may reach this cluster, so they must stay visible in the CR that admission and review look at. |
| `enabled` | `boolean` | no | `false` |  |
| `expose_oauth_authorization_server` | `boolean` | no | `false` | Expose a mediated OAuth 2.0 Authorization Server (RFC 6749 + PKCE) for this cluster, advertised at `/.well-known/oauth-authorization-server` (RFC 8414), like OpenShift does for its own OAuth server.<br /><br />The proxy itself becomes the authorization server an external caller talks to — `issuer`, `authorization_endpoint`, `token_endpoint`, and `jwks_uri` are all this cluster's own proxy URLs — mediating the whole exchange with the configured `issuer_url` server-side. | `issuer_url` | `string` | no | `""` | Ignored when the `config_from` Secret carries an `issuer_url` key. Optional only so a `config_from`-only block need not restate it; an enabled provider must end up with a non-empty value from one side or the other. |

- an enabled OIDC provider requires a non-empty issuer_url and client_id, or a config_from reference supplying them — `!self.enabled || has(self.config_from) || (self.issuer_url != '' && self.client_id != '')`
- expose_oauth_authorization_server requires the OIDC provider to be enabled — `!self.expose_oauth_authorization_server || self.enabled`
